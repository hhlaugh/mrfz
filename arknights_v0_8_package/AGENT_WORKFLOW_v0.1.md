# Agent 指挥手册：v0.8 规则与棋盘升级

## 1. 使用原则：一次只交办一个阶段

不要对 Agent 说“把整个游戏按新规则全部改完”。这会导致它同时重写规则引擎、AI、UI、联机和卡池，难以审查，也容易破坏已完成的 Demo。

推荐流程：先让 Agent 只读审计，再要求它提交一个小阶段，跑完测试、检查 diff，确认后再进入下一阶段。每个阶段应有：输入文件、允许修改范围、明确不做事项、验收条件和交付报告。

## 2. 项目资料的优先级

发生冲突时，按以下顺序处理：

1. `GAME_RULES_v0.8.md`：战斗与胜负的唯一规则依据；
2. `BOARD_PROFILE_SCHEMA_v0.1.md` + `BOARD_PROFILE_SCHEMA_v0.1.json`：棋盘结构与 DIY 限制；
3. `ENGINE_MIGRATION_PLAN_v0.8.md`：工程实施阶段与验收步骤；
4. `arknights_operator_pool_v1.1`：干员数值/技能配置，不覆盖规则；
5. 当前仓库代码：反映当前实际实现，但不自动拥有修改规则的权力。

如果规则文档互相冲突或某个卡牌字段无法映射，Agent 必须先报告，不得自行修改设计目标。所有用户未明确授权的卡牌数值平衡调整都不属于本轮工程任务。

## 3. 每次开始前的通用提示词

```text
你正在维护一个已经可运行的浏览器卡牌游戏项目。它已有单机对战、机器人对战和房间码好友联机功能。你的任务是增量升级，不是重写项目。

规则唯一依据：
- docs/GAME_RULES_v0.8.md
- docs/BOARD_PROFILE_SCHEMA_v0.1.md
- docs/ENGINE_MIGRATION_PLAN_v0.8.md

干员卡池数据：arknights_operator_pool_v1.1.csv/json。它是待适配数据，不代表技能已经在引擎中实现。

硬性约束：
1. 先阅读现有代码和文档，不要假定目录结构；
2. 保持纯规则引擎与 UI/网络层分离；
3. 不得为了适配某个 UI 或 Agent 方便而修改规则；
4. 不得擅自改卡牌基础数值、费用、CD、退款、SP 和技能效果；
5. 所有技能动作/事件/目标选择器必须白名单校验，不执行任意代码；
6. 保留现有单机、机器人和好友联机能力；
7. 每次只完成本轮指定的 Phase，不提前改后续系统；
8. 先写/改测试，再实现功能；
9. 实际运行测试并报告原始命令和结果，不得虚报；
10. 完成后检查 git diff，说明文件变更、风险、未完成项。

若发现规则歧义或旧代码与规则冲突，先列出具体文件、函数、规则条款和影响，不得自行设计新规则。
```

## 4. Phase 0：只读审计提示词

```text
本轮只做 Phase 0 只读审计，禁止修改、创建、删除或格式化任何项目文件。

请完整检查仓库，输出：
1. 实际目录结构；
2. 规则引擎入口、状态模型、行动执行、战斗结算、技能/状态、胜负判定所在文件；
3. AI 决策入口与合法动作生成位置；
4. UI 棋盘渲染、卡牌部署交互、战斗日志位置；
5. 好友联机房间创建、加入、状态同步和权威状态位置；
6. 所有固定三路、固定前后排槽位、硬编码 lane 名称和目标排序的位置；
7. 当前测试、构建、lint 命令与结果（只运行安全、无副作用的检查）；
8. 对照 GAME_RULES_v0.8.md，做“已支持/部分支持/不支持/存在冲突”矩阵；
9. 给出分阶段修改方案、可能回归风险和建议文件范围。

不要实现功能，不要猜测测试结果。结尾明确声明本轮没有改动文件。
```

## 5. Phase 1–3：底层规则和引擎

### Phase 1 提示词：类型、schema、validator

```text
本轮只实施 ENGINE_MIGRATION_PLAN_v0.8.md 的 Phase 1。

范围：BoardProfile 类型、BoardProfile validator、默认棋盘 JSON、route_groups 语义校验、persistent_effects_json 类型、技能事件/动作/目标选择器白名单，以及旧 taunt_scope/floating 字段的只读适配器（仅在项目实际需要时）。

不要修改战斗结算、UI、AI、联机协议；不要改任何卡牌平衡数值。

先列拟修改文件和测试，然后实施。所有合法/非法输入都要有单元测试。完成后执行项目真实测试命令，并按统一交付格式汇报。
```

### Phase 2 提示词：多卡位战斗引擎

```text
本轮只实施 Phase 2：将固定三路和前后排单格改为 BoardProfile 驱动的动态卡位。

严格遵守：lane_order -> front before back -> slot_index；普通攻击每单位每个己方 combat phase 默认一次；route_group 内收集敌方候选目标；嘲讽优先于普通地面目标；同类别按目标路序、排、卡位编号排序；沉默/浮空等状态先用现有兼容逻辑，不要在本阶段同时重写全部技能 DSL。

经济、抽牌、疲劳、撤离、退款、CD 和 SP 规则保持不变。先让 standard_3x1x1 回归，再测试 2路/4路/前排多格/4v2。

不要修改 UI 和联机。提交完整的规则单元测试和回归结果。
```

### Phase 3 提示词：沉默、永续效果、技能 DSL、目标选择

```text
本轮只实施 Phase 3。

实现 persistent_effects_json 的动态有效值计算；silence 必须压制目标自己的技能和 suppressed_by 含 silence 的永续效果，但不阻止普通攻击、不阻止任何 SP 获取、不清空已有 SP、不清除已结算状态。taunt/floating 默认可被 silence 和 freeze 压制。freeze 仍封锁 SP、普通攻击和事件型技能；未标记 freeze 的持续光环默认保留。

补齐 on_attack_declared、on_attack_resolved、on_friendly_attack_declared；continuous 只做动态查询；if_else 使用动作开始前同一状态快照并只执行第一个满足分支；moved_target 必须绑定原 card_instance_id。

实现 AOE 目标快照、按序逐个结算、单体治疗最低 HP 比例优先和无合法目标不扣 SP。

不要改 UI/AI/联机，不要修改卡牌数值。每个行为都需要可复现测试和日志。
```

## 6. Phase 4–7：卡池、AI、UI、联机

### Phase 4 提示词：v1.1 卡池适配

```text
本轮只实施 Phase 4：导入并验证 arknights_operator_pool_v1.1.csv/json。

保留全部 card_id，不擅自改 cost/atk/hp/SP/CD/退款/技能数值。检查72张卡的数据、技能事件、动作、条件、target selector、persistent effects、summon token。

先输出每张 playable_enabled 卡的支持状态表：完全支持/缺少动作/缺少事件/缺少目标选择器/需要数据迁移。未知能力不得静默忽略；未实现能力的卡必须保持不可玩或被加载器拒绝进入正式对局。

不要把“JSON可解析”称为“卡牌可运行”，每张可玩卡至少增加针对核心技能的测试。输出 schema 校验报告与迁移报告。
```

### Phase 5 提示词：AI 与 UI

```text
本轮只实施 Phase 5：让现有 AI 和 UI 支持 BoardProfile。

UI 必须根据 lanes/front_slots/back_slots 动态渲染；部署只提供合法空位；卡位显示路、前后排和编号；战斗日志可定位目标卡位。AI 只能从规则引擎的合法动作 API 生成动作，不得复制自己的目标合法性判定或经济公式。

验证 compact/standard/wide/extended 和至少一个 4v2 棋盘可打完整局。保留旧棋盘视觉和已有操作流程，不做无关美术重构。
```

### Phase 6 提示词：DIY 棋盘编辑器与攻防模式

```text
本轮只实施 Phase 6：增加 DIY 棋盘创建界面和 siege 模式。

提供双方独立路数、每路前排/后排格数、route_groups、基地 HP、攻守身份、先手和完整轮次上限设置。遵循 BOARD_PROFILE_SCHEMA_v0.1；对非法配置即时提示原因。创建对局后冻结配置。

攻防模式 round_limit 是完整轮次，每轮双方各行动一次；上限到达时守方基地仍大于0则守方获胜。不得为攻防模式复制一套战斗系统或自动修改费用。

联机同步暂不在本阶段更改，除非当前项目架构要求必须增加纯数据接口；如有依赖先报告。
```

### Phase 7 提示词：联机与平衡验证

```text
本轮只实施 Phase 7：让好友联机同步 BoardProfile 和版本信息，并完成压力/平衡验证。

开局快照必须包含 rules_version、board_schema_version、board_profile 完整规范化数据、board_profile_hash、card_pool_version。房主/服务器校验配置；访客只能接受该配置，不能单方面覆盖。双方 hash 不一致时不得开始。

执行构建、规则、AI、联机协议测试；固定随机种子至少1000局模拟。汇报胜率、平均回合、基地剩余HP、部署/撤离循环净费用、干员出场率和技能触发次数。只报告真实跑出的数据，不以主观观察代替模拟。
```

## 7. 日常跟 Agent 讨论问题的指令模板

如果 Agent 提出一个大范围重构，先要求它回答：

```text
请先不要改代码。请指出该修改对应的规则条款、会影响的模块、是否改变既有行为、需要新增哪些测试、如何回滚。把“必要改动”和“可选重构”分开。没有得到我明确同意前，不做可选重构。
```

若 Agent 说“已完成”，要求它证明：

```text
请给出本次实际执行的测试/构建命令、通过和失败数量、关键测试名称、git diff --stat，以及仍未测试的路径。不要用代码阅读推测代替实际执行结果。
```

如果 bug 重现不稳定：

```text
请先构造最小复现用例，固定随机种子，记录初始 BoardProfile、双方牌组、动作序列和事件日志。先修规则引擎，不要先用 UI 特判绕过。
```

## 8. 推荐的 Git 使用方式

1. 开始前确保当前 Demo 可运行并保存一次基线提交。
2. 新建功能分支，例如 `feature/rules-v0.8-board-profile`。
3. 每个 Phase 单独提交，例如 `phase-1-board-schema`、`phase-2-slot-engine`。
4. 每次提交前检查 `git diff`、构建和测试结果。
5. 不要让 Agent 同时跨多个 Phase 改动；一个阶段验收后再开始下一阶段。
6. 每阶段可回滚，避免一次大型变更破坏原有好友联机。

如果使用云端 Agent 或 GitHub 网页端，先确认它连接的是同一个仓库和正确分支，并确认能执行项目构建/测试；只能浏览文件而不能运行环境的 Agent 不应承担 Phase 2 之后的实现验收。
