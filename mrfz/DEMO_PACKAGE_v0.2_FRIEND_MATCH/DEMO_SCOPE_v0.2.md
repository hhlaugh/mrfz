# 三路攻防卡牌游戏：最小可玩 Demo 范围 v0.2

> **规则依据：** `GAME_RULES_v0.7.md` 是唯一玩法规则依据。
> **本版变更：** 在保留单人对战机器人的基础上，增加“房主创建房间码、好友加入”的 1v1 联机模式。
> **重要原则：** Demo 与未来正式版使用同一套游戏规则和规则引擎。Demo 只缩小卡池和预设牌组，不另设战斗规则。

## 1. 最小可玩 Demo 的定义

玩家打开网页后可以选择：

1. **单人对战：** 选择预设牌组，与本地机器人对战。
2. **好友对战：** 一名玩家创建房间并成为主机，获得房间码；另一名玩家输入房间码加入。双方选择预设牌组、准备、起手换牌后进行 1v1 对局。

Demo 仍采用 16 种唯一卡牌定义：8 张干员、6 张战术、2 张支援；两套预设牌组各 20 张。使用 v0.7 的全部公共规则、状态判定、撤离与再部署、SP、战斗结算和疲劳规则。20 张牌组是测试配置，不改变正式构筑规则。

## 2. 技术架构

### 2.1 前端

- React + TypeScript + Vite。
- 单机和联机共用同一套 React 游戏界面组件。
- 单机模式由本地 `GameController` 驱动规则引擎和机器人。
- 好友模式由房主浏览器运行完整规则引擎；访客浏览器只发送动作请求并接收自己的玩家视图。

### 2.2 房主权威制

**房主浏览器是唯一的对局状态权威（host-authoritative）。** 房主浏览器持有完整 `GameState`，包括牌库顺序、双方手牌和随机数状态；每一项玩家动作均由房主端的同一套 `validateAction` 与 `applyAction` 验证和执行。

- 房主自己的操作：直接交给房主本地规则引擎。
- 访客的操作：访客发送 `ActionRequest`；房主验证发送者座位、当前行动权、阶段、目标、费用和规则合法性；合法才执行。
- 房主执行成功后增加 `stateVersion`，向房主和访客分别发送各自的 `PlayerView`。
- 访客不得提交完整状态、费用结果、伤害结果或胜负结果；只提交动作意图。
- 中继服务器只处理房间、座位和消息转发，不运行规则引擎、不判断战斗、不保存完整对局状态。

这适用于熟人间休闲测试，不是竞技级防作弊架构。房主运行游戏状态，因此技术上可以检查或修改本地状态。若未来需要公平竞技，应迁移为服务器权威制；本 Demo 不做这一步。

### 2.3 通信方案

- 使用 Node.js + TypeScript + Socket.IO 建立独立的轻量中继服务。
- 前端通过 Socket.IO Client 连接中继服务；生产环境使用 HTTPS/WSS。
- 中继服务使用房间通道转发消息；房间最多两名玩家。
- 不采用 WebRTC 直连作为首版方案，不要求玩家开放路由器端口。
- 中继服务和静态前端可以分别部署；中继服务必须运行在支持持久 WebSocket/Socket.IO 连接的 Node 服务环境。

### 2.4 目录建议

```text
project/
├── src/
│   ├── game/                 # 纯 TypeScript 规则引擎，不依赖 React/Socket.IO
│   ├── data/                 # 16 张卡牌与两套牌组
│   ├── ai/                   # 本地机器人策略
│   ├── client/               # 单机/联机控制器、网络客户端
│   ├── components/           # React 界面组件
│   └── views/                # 首页、牌组选择、房间大厅、换牌、对战、结算
├── relay-server/             # Node.js + Socket.IO 中继服务，不含游戏规则
├── tests/                    # 规则、AI、协议与联机测试

```

如果已有工程结构更合理，Codex 可以提出调整，但必须保持 `src/game`（或同等规则引擎模块）纯净，不得让 React 或 Socket.IO 进入规则引擎。

## 3. 游戏内容（保持不变）

- 16 种卡牌：8 干员、6 战术、2 支援。
- 两套预设牌组，各 20 张，同名卡不超过 2 张。
- A 牌组：部署循环与正面推进。
- B 牌组：控制、浮空与 SP 调度。
- 卡牌数据以 `DEMO_CARD_POOL_v0.3.csv/json` 为准；牌组以 `DEMO_DECKS_v0.1.csv` 为准。若数据与 `GAME_RULES_v0.7.md` 冲突，以规则文档为准并修正数据，不得自行改写规则。

## 4. 好友房间流程

### 4.1 创建房间

1. 玩家选择“好友对战 → 创建房间”。
2. 客户端向中继服务请求创建房间。
3. 服务端生成随机、易读的 8 位房间码（排除容易混淆的字符），创建两个座位：`host` 与 `guest`。
4. 创建者自动占据 `host` 座位，选择 A 或 B 预设牌组。
5. 页面显示房间码和“复制房间码”按钮，等待好友加入。

### 4.2 加入房间

1. 好友输入房间码。
2. 服务端确认房间存在、未开始、guest 座位空闲且未过期。
3. 加入者占据 `guest` 座位并选择预设牌组。
4. 双方在房间大厅看到对方连接状态与牌组选择。
5. 双方均准备后，房主点击开始；服务端不代替房主执行游戏规则。

双方可以选择同一套预设牌组；首版不强制牌组互斥。

### 4.3 换牌与开局

- 对局初始化、洗牌、起手 5 张和起手换牌均由房主权威状态处理。
- 双方各自只向房主提交自己的换牌选择；不得把另一方手牌或牌库顺序发送给访客。
- 双方都完成换牌后，房主使用规则引擎的随机流程决定先手，并广播开局结果。
- 起手换牌的具体规则遵循 `GAME_RULES_v0.7.md`。

## 5. 房间码与房间生命周期

- 房间码使用服务端安全随机数生成，建议 8 位大写字母/数字，并排除 `0/O`、`1/I/L` 等易混淆字符。
- 一个房间最多两名玩家：一个 host、一个 guest；第三人加入必须被拒绝。
- 房间码只用于定位房间，不等同于账号或长期身份。
- 未开始房间建议 15 分钟无活动自动过期；开始对局后房间保持到结束或断线处理完成。
- 对创建/加入尝试做基础频率限制，防止房间码枚举；同一房间不能通过重复 join 获得第二个座位。
- 房主关闭页面或长时间断线：本版不做主机迁移，对局判定为中断并关闭房间；界面需明确警告“房主离开将结束对局”。
- 访客短暂断线：对局暂停，保留房间 120 秒供原访客通过重连凭证恢复；恢复后房主重新发送该访客的最新 `PlayerView`。
- 不实现旁观者、聊天、好友列表、跨房间邀请、观战和主机迁移。

## 6. 网络状态与信息安全边界

### 6.1 PlayerView（必须）

完整 `GameState` 不得广播给访客。必须提供 `toPlayerView(state, viewerId)`，为不同玩家生成不同视图：

- 双方基地基本分、公开棋盘、公开单位状态、费用、回合、当前阶段和公开战斗日志可见。
- 玩家只能看到自己的手牌和自己的牌库具体顺序（通常 UI 仅显示牌库数量）。
- 对手手牌只能显示张数，不得包含卡牌 ID、卡名或顺序。
- 对手牌库只能显示剩余数量，不得泄露顺序。
- 技能选择、起手换牌等私有操作不得广播给对方，除非规则要求公开。
- 不发送 host 的 RNG seed、随机数状态、完整牌库数组或内部调试字段。

### 6.2 动作协议

访客只提交动作请求，建议字段：

```ts
interface ActionRequest {
  requestId: string;
  expectedStateVersion: number;
  action: GameAction;
}
```

- `playerId`/座位由服务器连接上下文确定，不能信任访客 payload 自带的玩家身份。
- 房主收到后检查请求是否重复、`expectedStateVersion` 是否过期、请求方是否为当前行动玩家，再调用规则引擎验证。
- 重复 `requestId` 不得重复执行；状态版本过期时拒绝并向访客发送最新视图。
- 成功动作使 `stateVersion` 单调递增；房主向双方发送各自过滤后的视图和对应公开事件。
- 非法动作只返回错误，不得扣费用、移手牌或修改状态。
- 服务器检查消息大小、房间成员资格和基本频率；不负责判断游戏动作是否合法。

### 6.3 连接与版本

- 客户端连接时发送 `protocolVersion`、`rulesVersion`、`clientBuild`。
- 房间双方版本不兼容时禁止开始对局，并提示刷新到同一版本。
- 访客重连使用独立的 seat reconnect token；不要把 token 放进房间码或公开日志。
- 任何网络恢复都以房主当前状态快照为准，不通过重放过期客户端状态恢复。

## 7. UI 页面范围

1. 首页：单人对战、好友对战。
2. 单人牌组选择：A/B 预设牌组。
3. 好友对战入口：创建房间、输入房间码加入。
4. 房间大厅：房间码、复制按钮、双方牌组、准备状态、开始按钮、连接状态。
5. 起手换牌：双方私有显示各自手牌，互不泄露。
6. 对战页面：沿用单机版三路棋盘；增加网络状态、对手连接状态，不另做一套棋盘。
7. 结算页面：胜负、基本分、回合数、结束原因、再来一局/返回大厅。

## 8. 本版不做

- 账号系统、长期用户 ID、好友列表。
- 公共房间列表、随机匹配、排位、排行榜。
- 3 人以上、旁观者、聊天、观战。
- WebRTC 直连、语音/视频。
- 主机迁移、云端保存完整对局、跨设备恢复房主状态。
- 竞技级反作弊或服务器权威战斗计算。
- 联机专属规则或联机专属卡牌效果。

## 9. 验收标准

### 单机回归

- v0.7 所有规则测试仍通过。
- 单机玩家对机器人完整对局可进行，不依赖网络房间服务。

### 房间与连接

- 房主创建房间获得唯一房间码；好友能加入。
- 错误、过期、已开始或已满房间码会被拒绝并显示明确原因。
- 第三名玩家不能加入。
- 双方能选择牌组、准备、各自换牌并开始。
- 双方看到相同公开棋盘、回合、费用和战斗结果。

### 权威与隐藏信息

- 只有当前行动玩家可以提交动作。
- 客户端不能自行提交新 GameState、费用、伤害或胜负结果。
- Guest 发来的非法操作被 host 拒绝且状态不变。
- Guest 永远收不到对手手牌内容、对手牌库顺序或 host RNG 状态。
- 重复请求不会重复扣费或执行效果。
- 旧 stateVersion 的请求被拒绝并触发视图同步。

### 断线与恢复

- Guest 断线时对局暂停，120 秒内用原凭证重连可恢复。
- Guest 恢复后收到最新 PlayerView，而不是旧缓存状态。
- Host 退出或超过约定断线时限时，对局中断并清理房间；页面明确说明首版不支持主机迁移。

### 发布

- 前端静态站点可公开访问。
- Socket.IO 中继服务有公开 WSS 地址，生产 CORS 只允许正式前端来源。
- 两个不同浏览器配置文件/设备通过房间码完成一局测试。

## 10. Codex 开发原则

- 先完成本地规则引擎和单机 Demo，再做联机；不允许先写网络功能再补规则。
- 联机只增加 `relay-server`、网络控制器和好友房间 UI，不得复制一套规则引擎。
- 房主本地操作和访客远程操作都调用同一 `validateAction` / `applyAction` 路径。
- 每个阶段先读取规则与范围文档，只完成当前里程碑。
- 每个里程碑运行测试、汇报实际命令与结果，再等待用户确认进入下一阶段。
